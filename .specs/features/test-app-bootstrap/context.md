# Test App Bootstrap Context

User decisions captured across 3 `AskUserQuestion` rounds (2026-07-14), following two research passes into the current DI graph's capabilities. This ended up being the largest architectural change of this session -- it touches Milestone 1's foundational bootstrap sequencing AND ripples into every Milestone 3 pipeline-stage type (Middleware/Guard/Interceptor/Filter, all of which call `MustInject` in their own builder closures).

## Discovery 1: interface-typed injection does not exist today

`internal/inject.MustInject[T]` requires `T`'s `reflect.Kind()` to be `Pointer` -- panics otherwise (`inject.go:104-106`). `internal/resolver.Find`/`Provider.ResolvedType()` match by EXACT `reflect.Type` equality only -- no `Implements()` check exists anywhere. This directly conflicts with INSIGHT.md's "exemplo de Testing" section, which already documents (even before this session touched it) that `UserController` must depend on `IUserService`, not `*UserService`, for `MustOverride[IUserService]` to have anything to intercept.

## Discovery 2: the placeholder+copy-in-place trick does NOT generalize to interfaces

`MustInject[T]`'s current mechanism: allocate `placeholder := reflect.New(t.Elem())` (a real, stable, concrete pointer, e.g. `*UserService`), return it immediately to the caller, and LATER (Stage 3) mutate the memory IT points to via `placeholder.Elem().Set(real.Elem())`. This works because the POINTER VALUE itself never changes -- the caller's variable holds a stable address, and the callee later fills in the pointee's contents at that same address.

For an interface type `T`, there is no equivalent stable handle: `reflect.New(t)` for an interface `t` gives `*T` (pointer-to-interface-storage), but `MustInject[T]() T` must return a BARE `T` value (to match call sites like `userService := gonest.MustInject[IUserService](controller)`) -- dereferencing `*T` now to produce that bare value creates an independent COPY of the (still-nil) interface, disconnected from whatever `*T`'s memory gets mutated to later. Unlike the pointer case, there is no live indirection left once a bare interface value has been copied out. Go's `reflect` package also cannot synthesize an arbitrary dynamic proxy implementing an unknown interface at runtime (no codegen) -- so a "smart wrapper that forwards calls" workaround isn't achievable generically either.

**Conclusion**: interface-typed `MustInject[T]() T` genuinely cannot reuse the CURRENT "declare early during Stage 2, get a value that becomes valid once Stage 3 finishes" pattern. Presented 3 options to the user; they picked a 4th, better one (see Decision 1 below).

## Discovery 3: Provider-to-Provider dependencies ALSO use `MustInject`+placeholder today (not a separate mechanism)

Investigated `internal/resolver/stage3.go`'s `callConstructor`: a Provider's `Constructor(fn)` ONLY ever accepts `func()`, `func() (T,error)`, `func(context.Context) T`, or `func(context.Context) (T,error)` -- NO other dependency params are ever passed into a constructor call. This means the Emitter example in INSIGHT.md (`provider.Constructor(func(emitter *gonest.Emitter) *UserService {...})`) is aspirational/future (Emitter is explicitly listed under ROADMAP's "Future Considerations", not built) -- it does NOT reflect how Provider-to-Provider dependencies actually work today.

The REAL mechanism: a Provider's OWN builder closure calls `gonest.MustInject[*OtherProvider](provider)` (same public function every other pipeline-stage type uses), BEFORE calling `provider.Constructor(...)`, capturing the dependency in a variable the constructor closure then uses. `Provider` is itself a valid `module.Owner`, so its `MustInject` calls get recorded as `PendingEdge`s exactly like a Controller's or Guard's -- Stage 3's topological resolution (errgroup-based, cycle-detecting) handles Provider-to-Provider edges and Controller/Guard/etc-to-Provider edges TOGETHER, in one unified pass, today.

## Decision 1: reorder bootstrap -- resolve the full Provider graph BEFORE declaring Controllers/Guards/Middleware/Interceptors/Filters

**Chosen** (user's own proposal, after being presented the interface-injection blocker): split what is currently ONE unified declare-then-resolve pass into TWO phases:

1. **Provider phase** (unchanged internally): declare every `*Module`'s own `Providers()`, run each Provider's builder closure (their OWN `MustInject` calls target ONLY other providers, since providers never depend on controllers), then run Stage 1-3 exactly as today (errgroup-based parallel topological resolution, placeholder+copy-in-place, cycle detection) -- resolves the ENTIRE provider graph to REAL, final values.
2. **Consumer phase** (NEW): only once phase 1 fully completes, run every `*Module`'s own `Controllers()`/pipeline-stage types' (`Middleware`/`Guard`/`Interceptor`/`Filter`) builder closures. Their `MustInject[T]`/`MustInjectAll[T]` calls, made DURING this phase, can now resolve DIRECTLY against the already-fully-resolved provider set -- exact-match OR (new) `Implements()`-match, returning the REAL value immediately, no placeholder, no deferred copy-in-place, no `PendingEdge` bookkeeping needed for this phase's calls at all.

**Rejected**: keeping the current single unified pass and inventing a workaround return-shape for interface injection (returning `*T` instead of `T`, or resolving only from within `Route.Handler` per-request) -- user explicitly rejected per-request resolution ("vai precisar resolver toda vez que chegar uma requisição") and the `*T`-indirection workaround, in favor of fixing the ROOT ordering problem instead. This is a bigger change but produces a STRICTLY SIMPLER final mechanism for the consumer phase (no placeholder machinery needed there at all, for EITHER pointer or interface types) -- it's not just "the least-bad option," it's architecturally cleaner than what exists today for that phase.

**Why this doesn't break anything already built**: Providers never depend on Controllers/Guards/Middleware/Interceptors/Filters (no example anywhere, in INSIGHT.md or any feature built this session, has a Provider's Constructor depending on a Controller or pipeline-stage type) -- the two phases are naturally acyclic relative to each other. The provider-phase mechanism (placeholder+copy-in-place+topological+errgroup) is UNCHANGED, zero regression risk there by construction (same code path, just now scoped to run to completion before phase 2 starts instead of interleaved with it).

## Decision 2: `MustInject[T]`/NEW `MustInjectAll[T]`, both usable from Controller/Guard/Middleware/Interceptor/Filter builder closures (phase 2), NOT from within `Route.Handler`

**Chosen**: `MustInject[T]`/`MustInjectAll[T]` (T interface, multi-binding case) are called ONCE, during a pipeline-stage type's OWN builder closure (same timing every existing `MustInject[*Concrete]` call already uses today, e.g. `authService := gonest.MustInject[*AuthService](guard)` BEFORE `guard.Handler(...)`) -- resolved once at declare time (now phase 2, post-provider-resolution), captured by the `Handler`'s closure for later per-request use. Explicitly NOT resolved fresh on every incoming request (user's own reasoning: re-resolving per request would be wasteful and inconsistent with how every other `MustInject` call in this codebase already works).

**Impact**: `MustInject[*Concrete]`'s call-site SHAPE is UNCHANGED (same signature, same call position, same "capture in a variable before `Handler`" pattern) -- only its INTERNAL mechanism changes (direct lookup instead of placeholder, now that phase ordering guarantees providers are ready). This should be a source-compatible, behavior-compatible change for every EXISTING pointer-typed `MustInject` call site in this codebase (Controller/Guard/Middleware/Interceptor/Filter's own already-shipped tests) -- the whole point of moving the DI graph resolution earlier is that it changes internal implementation, not any consumer's observable behavior, for the pointer case. This must be verified rigorously (T0's own dedicated evaluator pass, full suite, zero test-assertion changes allowed -- same bar as AD-012/AD-013's own "already-shipped code" refactors).

## Decision 3: `MustInjectAll[T]` semantics

**Chosen**: `T` MUST be an interface kind (panics otherwise -- pointer types have no "multiple implementations" concept, `MustInject[T]` already covers the single-match case). Returns `[]T`, one entry per registered Provider whose resolved concrete type satisfies `T` (exact interface match OR `Implements()`), in some STABLE but not necessarily meaningful order (registration order across the module tree is the simplest deterministic choice -- design.md to confirm). Zero matches returns an empty slice (NOT a panic -- "give me all of them" reasonably tolerates "there are none," unlike `MustInject[T]`'s single-match contract which panics on zero because a caller asking for exactly one clearly expects one to exist).

## Discovery 4: Middleware/Guard/Interceptor/Filter run their builder IMMEDIATELY (AD-008), before `NewApp` is ever called -- Decision 1's "phase 2" cannot reach them

AD-008 (STATE.md) established that `Middleware`/`Guard`/`Interceptor`/`Filter` run `New(fn)` IMMEDIATELY (same as `route.New`), unlike `Provider`/`Controller`/`Module`, which defer `fn` until `Declare()` runs during bootstrap. In practice, these types are almost always constructed as PACKAGE-LEVEL `var`s (`var AuthGuard = gonest.NewGuard(func(guard){...})`, per every INSIGHT.md example) -- Go runs package-level var initializers during package `init()`, BEFORE `main()` even starts, which is unconditionally BEFORE any call to `NewApp`. This means any `MustInject` call inside one of these 4 types' builder closures has ALREADY RUN by the time `NewApp` (and therefore Decision 1's "phase 1 resolves providers, phase 2 declares consumers" split) begins -- there is no "phase 2" moment for these types to defer into, because their builder already finished executing long before bootstrap starts. Decision 1's reordering, as originally conceived, can only ever help `Controller` (which genuinely DOES defer via `Declare()`) -- it does nothing for the 4 immediate-execution types, which remain stuck with the exact placeholder-based mechanism Discovery 2 already proved cannot support interface types.

**Resolution -- AD-008 itself gets reconsidered**: `Middleware`/`Guard`/`Interceptor`/`Filter` change from immediate `New(fn)` execution to DEFERRED execution (same `Declare()`-based pattern `Provider`/`Controller`/`Module` already use) -- their builder closures (and any `MustInject`/`MustInjectAll` calls inside them) now run during bootstrap, not at package-init time. This reopens the EXACT ownership question AD-008 was created to sidestep: these 4 types can be attached to MULTIPLE controllers across MULTIPLE different modules (`controller.Guards(sameGuardVar)`, reusable) -- there is no single natural "owner module" the way a `Provider` has (imposed by the DI graph via `Module.Providers`).

## Decision 4: ownership for Middleware/Guard/Interceptor/Filter = the UNION of every module that references it, discovered post-assembly

**Chosen**: since a `Guard`/`Middleware`/`Interceptor`/`Filter` value doesn't know in advance which Controllers will attach it (`controller.Guards(g)` etc are called from WITHIN each referencing Controller's own builder closure), its true "ownership" can only be determined AFTER Stage 1 (`root.Assemble()`) has fully walked the module tree and every Controller has been enumerated -- at that point, the SET of Controllers referencing a given `*Guard` (etc) is known, and therefore so is the SET of MODULES those Controllers belong to (via `Controller.OwnerModule()`, already exists). That type's own `Declare()` (now deferred, per the resolution above) runs with an EFFECTIVE search scope equal to the UNION of (each referencing module's own providers + each of THOSE modules' visible exported-imports) -- `MustInject`/`MustInjectAll` called from inside it search across that unioned set, not a single module's scope the way `Controller`'s own `MustInject` calls do. If the SAME type ends up referenced by controllers in modules whose respective provider sets both happen to satisfy an interface (a genuine cross-module ambiguity), that's a legitimate "2+ matches" panic -- same "trust the caller, panic on real ambiguity" stance as every other resolution rule in this codebase, not a new special case to design around.

**Rejected**: a workaround where these 4 types search the ENTIRE global provider set (root + every imported module, no module-scoping at all) -- user explicitly wanted a REAL ownership model (preserving module encapsulation for these types, same as Controllers already have), not a shortcut that abandons module boundaries entirely just because ownership is harder to pin down for shared pipeline-stage types.

**Impact on Decision 1's phasing**: the two-phase bootstrap becomes THREE conceptual steps: (1) resolve the full Provider graph (unchanged), (2) determine ownership (referencing-module sets) for every Middleware/Guard/Interceptor/Filter by walking the now-fully-declared Controller tree -- but WAIT, Controllers themselves are declared in "phase 2" per Decision 1, and Controllers are what REFERENCE Guards/etc (`controller.Guards(g)` is called FROM WITHIN a Controller's own builder closure) -- so ownership discovery for Guards/etc can only happen AFTER Controllers have ALREADY run their own builders and recorded which Guards/Middleware/Interceptors/Filters they reference. This means the REAL final ordering is: **Provider phase → Controller phase (Controllers declare, recording which pipeline-stage-type values they reference via `Guards()`/`Use()`/`Interceptors()`/`Filters()`, but NOT yet running those referenced types' OWN builder closures) → Pipeline-stage-type phase (NOW, with full referencing-module sets known, each Guard/Middleware/Interceptor/Filter's OWN deferred builder closure runs, with its union-scoped search available)**. This is a genuine THIRD bootstrap phase, not just two -- design.md must work out the exact mechanics (a `New(fn)` call for these 4 types can no longer run `fn` immediately NOR even eagerly defer to a plain `Declare()` the way `Controller` does, since it specifically needs to wait for `Controller`-phase to finish recording every reference to it first).

## Underlying rationale (user's own framing, ties everything above together)

The whole point of the `New*(func(x *X){...})` builder shape throughout this codebase (`NewProvider`, `NewController`, `NewGuard`, `NewMiddleware`, `NewInterceptor`, `NewFilter`) is to SIMULATE a class-with-constructor OOP pattern in Go: the closure body plays the role of a constructor body, and anything it does to "organize the instance" (including grabbing its own dependencies via `MustInject`) should behave like real constructor-injection (NestJS's own `constructor(private service: SomeService)`) -- the dependency should already be a REAL, usable value at that point, not a promise/placeholder that becomes valid at some later, unrelated time. This is PRECISELY why Provider-graph resolution (Stage 1-3) must complete BEFORE any `New*` builder that calls `MustInject` runs -- every phase-ordering decision above (Decision 1, Decision 4) is in service of this one underlying principle, not an arbitrary implementation convenience. `Provider` already gets this right for provider-to-provider deps (Stage 1-3 IS this, today). `Controller`/`Middleware`/`Guard`/`Interceptor`/`Filter` need to be brought in line with the SAME principle -- which is exactly what this feature's 3-phase bootstrap achieves for all of them, uniformly, not just as a workaround for the interface-injection problem that originally surfaced it.

## Scope boundary

This feature ("Test App Bootstrap") now covers BOTH the bootstrap reordering (Provider-phase-then-Consumer-phase split) AND the new interface-aware `MustInject`/`MustInjectAll` built on top of it AND `MustNewTestApp`/`TestBuilder`/`MustOverride[T]` (the ORIGINAL Milestone 8 ask). The bootstrap reorder is a PREREQUISITE the other two decisions depend on -- it gets its own isolated, maximally-scrutinized task (see tasks.md), given it's the highest-risk change of this entire session (touches Milestone 1's core bootstrap AND every Milestone 3 pipeline-stage type's existing test suite). The SEPARATE "HTTP Test Client" ROADMAP feature (`MustRequest`/`AssertStatus`/`AssertJsonPath`) still builds on top of whatever `MustNewTestApp` returns, not addressed in this feature.
