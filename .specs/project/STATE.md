### AD-029: Unified Parse API — `Parseable` interface em `execution`, `BodySource` opaque-carrier, wiring em `internal/app` (2026-07-17, EXECUTADO -- corrige encoding quebrado + local de wiring do AD-025 duplicado abaixo)

**Decision:** `Parse[T]`/`MustParse[T]` substituem os 8 pares legacy `MustParseRest*`/`ParseRest*`. O tipo `Parseable` vive em `internal/execution` porque `validate` já importa `execution` -- inverter criaria ciclo. **CORREÇÃO pós-execução:** `Parseable`'s método NÃO pôde ficar unexported como o design original previa -- Go trata dois identificadores unexported como DIFERENTES quando declarados em pacotes diferentes (spec: "Two identifiers are different if... they appear in different packages and are not exported"), então um método unexported declarado em `execution` nunca seria satisfeito por um método de mesmo nome declarado em `validate` (onde TODAS as implementações concretas -- `paramsSource`, `querySource`, `jsonBodySource`, `formBodySource`, `headersSource` -- precisam viver, pra reusar `resolveSchema`/`validateValue`/`populate` sem duplicar). **Reason:** a API atual (funções source-específicas) não é extensível sem modificar o callsite público -- adicionar XML ou headers exige uma nova função raiz. O padrão `Parseable` desacopla fonte de parseamento da API pública -- qualquer `ctx.XxxSource()` pode retornar um `Parseable` novo sem tocar `Parse[T]`/`MustParse[T]`.
**Trade-off:** breaking change imediata (sem deprecation): todos os 8 pares legados removidos de vez. `Parseable` com método EXPORTADO (não unexported como planejado) significa que, tecnicamente, qualquer pacote externo PODE implementar a interface -- mitigado na prática porque as structs concretas (`paramsSource` etc) continuam unexported em `validate`, só acessíveis via as funções construtoras exportadas (`NewParamsSource` etc). `BodySource` como carrier opaco em `execution` aumenta o acoplamento conceitual desse pacote (antes folha pura) -- aceito porque já carregava `WithRoute` pelo mesmo motivo.
**Impact:** `internal/execution/context.go` ganha `Parseable`, `BodySource`, `WithSources`, `NewBodySource`; `internal/execution/formfile.go` (novo) ganha `FormFile`/`NewFormFile`. `internal/app/app.go` ganha import de `internal/validate` e chama `WithSources` dentro de `withRoute`. `gonest.go` re-exporta `Parseable`/`FormFile` como type alias, expõe `Parse[T]`/`MustParse[T]`. 8 funções legadas removidas de `gonest.go`+`internal/validate/{validate,params,query,form}.go`. Todo call site interno migrado (`gonest_test.go`, `internal/app/*_test.go`, `internal/validate/*_test.go` via helpers `mustParseParams`/etc, `.examples/simple-todo`, `.examples/blog-api`). `INSIGHT-PARSE.md` corrigido (2 bugs no sketch original: `RoutePatch` inexistente → `Route(gonest.HttpPatch, ...)`, `Form()` sem argumento → `Form(nil)`), confirmado compilando via build real num módulo de exemplo. **Decision:** Nova feature especificada (`.specs/features/graphql-support/{spec,context}.md`) evoluindo o rascunho `INSIGHT-GRAPHQL.md` -- `gonest.NewResolver`/`resolver.Query`/`Mutation`/`Subscription` como nova ponta de exposição GraphQL, análoga a `Controller` pra REST. Query/Mutation usam `Handler(func(ctx *GraphqlContext) any)` -- retorno direto vira o `data` do resolver, sem `Response`/`.Data()` separado (GraphQL não tem status/headers pra justificar isso, igual NestJS: "ele apenas pega o retorno e já trata como data"). Subscription usa assinatura própria (`Handler(func(ctx, emit func(any)))`, é STREAM não request-response) e reaproveita `gonest.Emitter` via um método NOVO `Emitter.Subscribe[T](done <-chan struct{}) <-chan T` (canal dinâmico, cancelado quando `done` fecha -- complementar ao `MustOn`/`Emit` estáticos já existentes). Geração automática de SDL a partir do MESMO `gonest.Schema` de REST -- branches de formato (`Email`/`Uuid`/`DateTime`/etc) viram Custom Scalars; `Custom(fn)` ganha `.GraphqlScalar(name)` pra tipos sem `format` OpenAPI nativo (ex: `primitive.ObjectID` do MongoDB), deduplicado por nome igual `$ref`/`components.schemas` já dedupam por identidade.
**Reason:** motor GraphQL por baixo foi decidido via PESQUISA REAL (WebSearch + `gh repo view`/`gh issue view`, não assumido): `gqlgen` é schema-first (exige `.graphql` escrito à mão + `go generate`), colidindo com a filosofia 100%-runtime de `Schema`/`PropertyBuilder`. `graphql-go/graphql` é code-first (schema montado via `graphql.NewSchema(...)` direto em Go) -- alinhado. Confirmado ativo (`gh repo view`: push em 2026-06-23, 10k+ stars, não arquivado). A limitação real encontrada (issue #49 do repo, fechada em 2016, mostra que Subscription só ganhou suporte SINTÁTICO, nunca um motor de execução/streaming pronto) foi avaliada e NÃO pesou contra a escolha -- o gonest já ia construir sua própria camada de execução via `Emitter.Subscribe` de qualquer forma, então o que `gqlgen` daria de graça (motor de subscription pronto) não seria aproveitado do mesmo jeito mesmo se disponível.
**Trade-off:** aceito conscientemente que o gonest terá que escrever sua PRÓPRIA solução de transporte de Subscription cobrindo SSE e WebSocket -- nenhum dos dois vem pronto de `graphql-go/graphql`. Protocolos de referência (`graphql-ws`/`graphql-transport-ws` pra WS, `graphql-sse` pra SSE) existem como especificação pública, servem de guia de compatibilidade com clients existentes mesmo implementando por conta própria. Erro dentro de Subscription (canal de erro próprio, fechamento gracioso por client) reconhecido como gap real, deixado fora de escopo desta spec (Edge Cases documentam isso explicitamente, não escondido).
**Impact:** `ROADMAP.md` ganha Milestone 16 (status SPECIFIED). `INSIGHT-GRAPHQL.md` atualizado com a decisão de motor + a consequência do transporte próprio. Milestone 15 (Schema Value Support) continua sendo a PRÓXIMA a ser EXECUTADA (já tem tasks.md completo) -- Milestone 16 é só Specify por ora, Design/Tasks pendentes pra quando entrar em pauta de execução.

### AD-031: Milestone 15 (Schema Value Support) especificada via brainstorming -- `Value[T]`→`Accessor[T]`, novo `NewValue[T]`/`Value` (2026-07-17)

**Decision:** Nova feature especificada (`.specs/features/schema-value-support/{spec,context,design,tasks}.md`) evoluindo o rascunho `INSIGHT-SCHEMA.md` -- permitir `gonest.NewValue[T](func(m *gonest.Value) {...})` pra construir um `*Schema` sobre um valor primitivo isolado (ex: `cpfSchema := gonest.NewValue[string](func(m *gonest.Value) { m.String().Min(11).Max(11).Pattern(...) })`), sem exigir `T` ser struct como `NewSchema[T]` hoje exige (`internal/schema.New` panica se `structType.Kind() != reflect.Struct`). Pré-requisito: `gonest.Value[T]` (dirty-tracking existente, `internal/value`) renomeia pra `gonest.Accessor[T]` -- mesma API (`Get`/`Set`/`IsDirty`/`OnDirty`/`Apply`), só o nome muda, liberando "Value" pro conceito novo. `gonest.Property(&t.X)` (dentro de `NewSchema[T]`, struct) permanece EXATAMENTE como está -- decisão explícita de não reformar por causa de um caso secundário.
**Reason:** brainstorming percorreu várias alternativas de nome antes de convergir: `NewProperty`/`Property` (reaproveitar o tipo já existente) foi descartado porque "Property" carrega a ideia de "parte de um todo" -- natural pro campo de struct (caso mais comum), estranho pro valor raiz que não é parte de nada. `NewPrimitive`/`Primitive` foi a primeira escolha alternativa (funcional, sem colisão), mas o usuário preferiu `Value` por soar mais coerente -- exigindo repensar o `Value[T]` já existente. `Scalar` foi cogitado e descartado por engessar a leitura pro contexto GraphQL especificamente. Pro rename do `Value[T]` atual: `Dirty[T]` foi cogitado primeiro (o padrão tem nome próprio na literatura, "Dirty Flag pattern", Nystrom) mas descartado -- "dirty" é um ESTADO exposto via `IsDirty()`, não o que o tipo É, nomear o TIPO pelo estado transitório é estranho. `Accessor[T]` (termo correto da literatura de OO pra "algo com get/set") foi a escolha final.
**Trade-off:** `Value[T]`→`Accessor[T]` é uma mudança de código REAL (não hipotética como o resto da reflexão) -- `internal/value`, usado hoje em PATCH-style handlers. Framework pré-1.0, custo baixo agora. Nenhum uso de `gonest.Value[T]` encontrado em `.examples/*` nesta sessão (só em `gonest.go`'s próprio re-export) -- migração de call sites deve ser pequena. Design técnico de COMO `internal/schema` produz o `PropertyBuilder` implícito (alias direto de `PropertyBuilder` vs tipo novo, construtor separado vs flag em `New`) deixado em aberto pro Implementer decidir durante a execução (T3 do tasks.md), documentado explicitamente como decisão pendente em vez de fixado prematuramente.
**Impact:** `ROADMAP.md` ganha Milestone 15 (status SPECIFIED). `INSIGHT-SCHEMA.md` (repo root) continua como o rascunho original da reflexão -- será atualizado pra refletir a implementação real só depois da execução (T6 do tasks.md). Execução (rodar os 7 Implementers/Evaluators) pendente pra próxima sessão.

### AD-023: `Route.FormBody` -- OpenAPI documentation pra `multipart/form-data`, revertendo o "Out of Scope" original da feature (2026-07-15, Milestone 12 T7)

**Decision:** `Route.FormBody(m *schema.Schema, fileFields ...string)` (novo, `internal/route/route.go`) documenta o requestBody como `multipart/form-data` em vez de `application/json` -- schema INLINE (nunca `$ref`/registrado em `components.schemas`, diferente de `RequestBody`) combinando as properties do `m` (chaveadas pela tag `form`, via `tagName(p, "form")` -- NÃO `tagName(p, "")`, que cairia no nome puro do campo Go já que um campo `form:"..."` tipicamente não tem tag `json`) com uma property `{"type":"string","format":"binary"}` por nome em `fileFields` (convenção OpenAPI 3.1 pra "isso é um arquivo").

**Trade-off:** nenhum técnico -- puro acréscimo de API, reaproveitando `schemaFor`/`tagName` como estão. `Route.RequestBody`/`Route.FormBody` são mutuamente exclusivos na prática (uma rota tem UM corpo só), gerador verifica `FormBody` primeiro, `RequestBody` como fallback -- nenhuma validação impede os dois juntos, mas nenhum caso de uso real pediria isso.
**Impact:** `.examples/blog-api`'s rota `POST /posts/:post_id/attachment` ganhou `r.FormBody(uploadAttachmentFormDTOSchema, "file")`, confirmado ao vivo via `/openapi.json` que o schema aparece certo (`description`+`file` com `format: binary`). ### AD-021: `gonest.Context`→`RestContext`; `MustParams`/`MustQuery`/`MustJsonBody` cada um vira um PAR `ParseRestXxx` (retorna `(T, error)`) + `MustParseRestXxx` (panica) (2026-07-15)

**Decision:** `gonest.Context` → `gonest.RestContext` (alias raiz só -- `internal/execution.Context` NÃO renomeado, só o re-export público muda). `MustParams`/`MustQuery`/`MustJsonBody` cada um vira 2 funções: `ParseRestParams[T](ctx, m) (T, error)`/`ParseRestQuery[T](ctx, m) (T, error)`/`ParseRestJsonBody[T](ctx, m) (T, error)` (núcleo, nunca panica em falha de VALIDAÇÃO -- devolve `*exception.BadRequestException` como `error`) + `MustParseRestParams[T](ctx, m) T`/`MustParseRestQuery[T](ctx, m) T`/`MustParseRestJsonBody[T](ctx, m) T` (wrapper fino, chama o `Parse*` e panica se `err != nil`). `resolveSchema`'s panic de mismatch de tipo (AD-019) continua panic PURO em ambas as variantes -- é bug de programador (schema errado passado), categoria diferente de "requisição do usuário falhou validação", nunca devia virar `error` de request. `internal/exception.HttpException` ganhou `Error() string` (retorna `e.message`) pra toda exception (built-in ou dev-defined) satisfazer a interface `error` do Go de graça, sem wrapper novo.
**Reason:** brainstorming do usuário sobre unificar `MustParams`/`MustQuery`/`MustJsonBody`/`MustHeaders` num `MustParse[T](ref, schema)` só -- descartado (ver discussão: `ref any` perde a info de qual tag/algoritmo usar, params e query provavelmente compartilham o mesmo tipo Go de retorno então nem dá pra discriminar por tipo de `ref` sem wrapper type novo, e `MustJsonBody` valida recursivo enquanto os outros validam plano, então o "1 nome só" só esconde o switch, não elimina). No meio da discussão, usuário decidiu manter os 4 nomes separados mas prefixar com `Rest` (`MustRestParams` etc.) -- justificativa: pretende atender GraphQL/gRPC/messaging além de REST (`INSIGHT-GRAPHQL.md`/`INSIGHT-GRPC.md`/`INSIGHT-MICROSERVICE.md` já criados pelo usuário), então "Rest" no nome sinaliza que esses `Must*`/`Context` são ESPECÍFICOS do adapter HTTP/REST, deixando espaço pra `gonest.GraphQLContext`/`gonest.GrpcContext` etc. no futuro sem colisão de nome. Ao confirmar o rename de `Context`, usuário percebeu que toda variante `Must*` "provavelmente precisa de uma versão que retorna erro também" -- daí o par `Parse*`/`MustParse*` em vez de só renomear.
**Trade-off:** dobra o número de funções exportadas nessa família (3 pares em vez de 3 funções), mas cada núcleo `Parse*` já existia internamente como lógica-que-panica -- extrair o núcleo (retornando `error` em vez de `panic`) e fazer `Must*` chamar+panicar é refactor mecânico, não duplicação de lógica de validação. `MustHeaders`/`ParseRestHeaders` citados no INSIGHT-OPENAPI.md continuam APENAS aspiracionais (headers validation nunca foi implementado) -- não construídos agora, só o nome final já documentado pra quando existir.
**Impact:** TODO call site de `gonest.Context`/`gonest.MustParams`/`MustQuery`/`MustJsonBody` reescrito (`gonest.go`, `gonest_test.go`, `internal/validate/{validate,params,query}.go` -- cada um ganhou `Parse*`/`Must*` internos --, `.examples/blog-api/{module/*/controller.go,shared/*.go}`, `.examples/simple-todo/controller.go`, `INSIGHT-MODULE.md`, `INSIGHT-OPENAPI.md`). Novo teste `TestParseRestParams_RootPackage_ReturnsErrorInsteadOfPanicking` (`gonest_test.go`) prova o caminho `error` de verdade (não só compila). Suite inteira (`go test ./... -race`) verde, zero mudança de asserção pré-existente -- toda chamada interna (`validate.MustParams` etc, usada extensivamente em testes já existentes) manteve o MESMO nome e assinatura (só ganhou uma implementação de 2 camadas por baixo).

### AD-020: Enum completo de status HTTP em `gonest.HttpStatus*` (2026-07-15)

**Decision:** `gonest.go`'s antigo par `HttpStatusOk`/`HttpStatusServiceUnavailable` (deliberadamente estreito, doc comment antigo dizia "not a full status-code enum") virou um enum completo com as 63 constantes padrão de `net/http` (`http.StatusContinue`...`http.StatusNetworkAuthenticationRequired`), cada uma um alias DIRETO do valor `net/http` correspondente (nunca um literal redeclarado, então nunca dessincroniza se `net/http` mudar). `TestHttpStatusConstants_MatchNetHttp` (novo, `gonest_test.go`) confere uma amostra (1 por classe + as fáceis de digitar errado -- Teapot, WebDAV) contra `net/http` diretamente.

Perguntado se cobria a lista completa do MDN (developer.mozilla.org/.../HTTP/Reference/Status) -- confirmado que `net/http` já espelha o mesmo registro IANA que o MDN documenta, então o enum novo já cobre tudo sem precisar consultar a página.

### AD-019: `MustParams`/`MustQuery`/`MustJsonBody` recebem o `*Schema` como argumento explícito, não mais um lookup por tipo num registry global (2026-07-15)

**Decision:** `MustJsonBody[T](ctx)`/`MustParams[T](ctx)`/`MustQuery[T](ctx)` → `MustJsonBody[T](ctx, m *Schema)`/`MustParams[T](ctx, m *Schema)`/`MustQuery[T](ctx, m *Schema)`, em `gonest.go` e nos 3 pontos reais (`internal/validate/{validate,params,query}.go`). `resolveSchema` (novo, `internal/validate/validate.go`) confere `m.StructType() == structType` ANTES de qualquer trabalho, panicando com mensagem clara ("gonest: schema mismatch") se o `*Schema` passado foi construído pra um tipo DIFERENTE de `T` -- necessário porque `Schema`'s field offsets são medidos contra o endereço-base do PRÓPRIO tipo que `NewSchema[T]` construiu (`internal/schema.New`'s doc comment), então validar/popular contra um `T` errado seria, na pior hipótese, misinterpretar memória via `unsafe`, não só um erro lógico. `internal/schema`'s registry (`Register`/`Lookup`/`Deregister`, `registry.go`) foi MANTIDO intacto -- `New`/`NewSchema[T]` continua registrando e panicando em dupla-declaração do mesmo tipo (proteção independente, não relacionada ao consumo de `Must*`), só que agora NADA em produção chama `Lookup` -- só o próprio `registry_test.go` ainda o exercita diretamente.
**Reason:** discussão explícita do usuário (brainstorming em cima da seção "hipótese" de INSIGHT-OPENAPI.md): o objetivo era obrigar o `*Schema` a existir e ficar acessível perto da rota que o usa, convertendo o footgun de hoje (schema nunca registrado só panica em runtime, na 1ª request real que bater na rota -- pior que `MustInject`, que já panica alto durante o bootstrap do `NewApp`) num erro de COMPILAÇÃO. A hipótese original propunha um MÉTODO no próprio `*Schema` (`ExParams.MustParseParams(ctx)`), descartado: exigiria `Schema` virar genérico (`Schema[T]`) com um core não-genérico por baixo pros usos atuais (`Route.Response`, registry, `Array`/`Object` nesting), e um método que precisasse de `*execution.Context`/`*route.Route` criaria ciclo de import de volta pra `internal/schema` (hoje pacote FOLHA, zero dependência própria, importado por `route`/`validate`/`openapi`/`exception`). Passar o Schema como ARGUMENTO explícito entrega a MESMA garantia (impossível compilar sem o valor em mãos) sem nenhum desses riscos. Deliberadamente NÃO aplicado a `MustInject`/`MustInjectAll` -- DI existe pra DESACOPLAR consumer de provider (amarrar num valor de `*Provider` reintroduziria esse acoplamento), e `MustInjectAll` já prova que não existe "o valor único" no caso multi-bind; além disso `MustInject` já panica alto no bootstrap do `NewApp`, sem o mesmo risco de "silencioso até tráfego real" que motivou essa mudança pro lado da Schema.
**Trade-off:** TODO call site de `MustJsonBody[T]`/`MustParams[T]`/`MustQuery[T]` no repo precisou de reescrita mecânica (adicionar o Schema como 2º argumento) -- `gonest_test.go`, `internal/validate/*_test.go`, `internal/app/{app,pipeline_ordering}_test.go`, `.examples/blog-api/module/{user,post,comment}/controller.go`, `.examples/simple-todo/controller.go`. Perde a leitura "só o tipo T já basta" que a chamada tinha antes (agora precisa segurar a variável do schema por perto), ganho é a obrigatoriedade em troca. 4 testes que provavam o antigo comportamento "tipo nunca registrado, panica" (`TestMustJsonBody_UnregisteredType_...`, `TestMustParams_UnregisteredType_...`, `TestMustQuery_UnregisteredType_...`) viraram testes de MISMATCH (passa um Schema construído pra um tipo diferente de T) -- é o equivalente moderno do mesmo cenário, já que "nunca chamar `NewSchema[T]`" não é mais um estado alcançável em compilação (não tem como ter um `*Schema` em mãos sem `NewSchema[T]` ter rodado).
**Impact:** suite inteira (`go test ./... -race`) verde, zero mudança de asserção fora das 3 renomeadas pra mismatch (mesmo comportamento observável, só o CAMINHO até o panic mudou). `internal/schema`'s registry sobrevive intacto (ver Decision acima) -- não foi removido, só deixou de ter consumidor em produção.

### AD-017: `Route.Response` passa a receber um callback `func(*Response)` (builder), não mais um `*Schema` variádico direto -- `Response` ganha `.Schema()`/`.Description()`; respostas 4xx/5xx sem schema explícito default pra `exception.Schema` (HttpException) (2026-07-15)

**Decision:** `Route.Response(status int, m ...*schema.Schema)` virou `Route.Response(status int, fn ...func(response *Response))`, onde `Response` (`internal/route/response.go`, reexportado como `gonest.Response`) é um builder com `Schema(m *schema.Schema) *Response` e `Description(s string) *Response`, cada um com getter correspondente (`SchemaValue() (*schema.Schema, bool)`, `DescriptionText() (string, bool)`) pro gerador ler de volta. Zero callback = "documentado, sem body" (igual ao zero-schema-args de antes). Junto disso, `internal/openapi`'s `buildResponses` ganhou um default: qualquer status 4xx/5xx documentado SEM `Schema()` explícito agora usa `exception.Schema` (novo, `internal/exception/schema.go` -- descreve o formato JSON de `HttpException`: `name`/`message`/`details`) como content, com `description` = `http.StatusText(status)` e um `example` cujo `name` é o nome do exception built-in daquele status quando existe (`NotFoundException` pra 404, etc) ou sintetizado do texto do status pros demais. `response.Description(...)` sempre sobrescreve a description default (auto-derivada OU vazia), pra qualquer status.
**Reason:** pedido explícito do usuário em 2 rodadas -- primeiro só queria conseguir setar uma description customizada por resposta (motivou uma primeira iteração, `Route.ResponseDescription(status, text)`, método separado); na sequência reescreveu o exemplo de Swagger no INSIGHT.md consolidando schema+description num único builder por resposta (`response.Schema(...)`/`response.Description(...)`), SUPERSEDENDO `ResponseDescription` (removido, nunca chegou a ser usado em exemplo real fora de teste). O default de `exception.Schema` pra 4xx/5xx sem body veio de uma reclamação concreta: abrindo `/openapi.json` do `.examples/blog-api`, toda resposta de erro documentada via `r.Response(404)` aparecia como `{"description": ""}`, zero informação -- já que `HttpException` é o carrier ÚNICO (built-in e dev-defined) de toda exception no framework, é sempre uma descrição verdadeira (ainda que genérica) do que aquele status de fato retorna.
**Trade-off:** API muda de "passa o schema direto" pra "passa uma função que configura o schema" -- 1 nível a mais de indireção por chamada (`r.Response(201, func(response *gonest.Response) { response.Schema(m) })` em vez de `r.Response(201, m)`), mas abre espaço pra crescer (mais métodos em `Response` no futuro) sem quebrar a assinatura de novo. `internal/exception` ganhou uma dependência nova de `internal/schema` (só nesse sentido -- não existia ciclo antes nem depois); `Response.Schema` não pôde ser construído via `gonest.NewSchema[T]` (genérico, definido em `gonest.go`, que já importa `internal/exception` -- importar de volta seria ciclo), resolvido duplicando a wrapper de 5 linhas de `NewSchema` localmente em `internal/exception/schema.go` (mesmo precedente de AD-004: duplicar wrapper pequeno é aceitável quando Go/ciclo de import não permite reexport).
**Impact:** TODO call site de `Route.Response(status, schema)` no repo precisou de reescrita mecânica pra `Route.Response(status, func(response *gonest.Response) { response.Schema(schema) })` (`gonest_test.go`, `internal/openapi/generate_test.go`, `internal/route/route_test.go`, `.examples/blog-api/module/{user,post,comment}/controller.go`). Suite inteira (`go test ./... -race`) verde; 1 teste pré-existente (`TestGenerate_UserEntityAddressEntity_FullReproduction`) teve sua ASSERÇÃO atualizada de propósito (esperava `{"description":""}` sem content pra um 400 sem body -- agora espera o default de `exception.Schema`), já que o comportamento observável mudou de propósito, não regressão.

### AD-015: Bootstrap de 3 fases (Provider → Controller → Pipeline-stage) + reversão de AD-008, pra viabilizar DI por interface (2026-07-14 especificado, 2026-07-15 EXECUTADO -- commit `450656a`)

**Decision:** `NewApp` reordenado em 3 fases: (1) resolve TODO o grafo de Provider primeiro (Stage 1-3 atual, inalterado internamente); (2) DEPOIS declara Controllers (cujo `MustInject` passa a resolver DIRETO, sem placeholder, já que providers estão prontos); (3) DEPOIS declara Middleware/Guard/Interceptor/Filter (que TAMBÉM passam a ter builder DEFERIDO -- reverte AD-008 -- porque hoje rodam `New(fn)` na hora, tipicamente em `var X = gonest.NewGuard(...)` a nível de pacote, ANTES até de `NewApp` ser chamado, tornando IMPOSSÍVEL adiar a resolução deles pra depois de qualquer fase de bootstrap). Ownership desses 4 tipos (que podem estar em múltiplos controllers/módulos, motivo original de AD-008) vira a UNIÃO dos módulos que os referenciam, descoberta DEPOIS que a fase de Controller termina. `MustInject`/novo `MustInjectAll` ganham suporte a tipo INTERFACE (hoje só ponteiro, panica em interface) -- exact-match OU `reflect.Type.Implements()` fallback, escopado (module-scoped pra Controller, union-scoped pra Guard/etc).
**Reason:** Milestone 8's primeira feature ("Test App Bootstrap", `MustOverride[Interface]`) expôs que DI por interface não existe hoje E que o mecanismo de placeholder+copy-in-place que TODO `MustInject` usa hoje genuinamente não generaliza pra interface (ponteiro é handle estável reescrito depois; valor de interface copiado por valor não tem essa indireção). 3 rodadas de `AskUserQuestion` levaram a essa solução: em vez de mudar a FORMA de retorno de `MustInject` (quebra ergonomia) ou resolver só dentro do Handler (resolve toda request, desperdício), resolver o grafo de Provider ANTES de qualquer `New*` builder que faça `MustInject` rodar -- alinhado com a filosofia original do padrão builder desses tipos (simular constructor de classe, onde dependência injetada já devia ser valor real, não placeholder).
**Trade-off:** MAIOR mudança arquitetural planejada nesta sessão -- toca Milestone 1 inteiro (`internal/inject`/`internal/resolver`/`internal/provider`/`internal/app`) E reverte uma decisão desta MESMA sessão (AD-008, Milestone 3). Timing de side-effects de Middleware/Guard/Interceptor/Filter muda (agora durante `NewApp`, não mais em package-init) -- suite existente PODE precisar de ajuste de QUANDO um teste checa algo, mas design.md exige ZERO mudança de asserção (O QUE é esperado nunca muda, só QUANDO checar).
**Impact:** especificação completa (`.specs/features/test-app-bootstrap/{context,spec,design,tasks}.md`) pronta, mas EXECUÇÃO NÃO INICIADA -- parado a pedido explícito do usuário dado o tamanho/risco. Próxima sessão deve reler tudo + o código atual (pode ter mudado) antes de despachar T0. Ver HANDOFF.md pra instruções detalhadas de retomada.

### AD-014: Schema Generation mapeia `@nestjs/swagger`'s `@Api*` decorators pra builder methods em `Controller`/`Route`/`Metadata` (2026-07-14)

**Decision:** `Controller.Tags`/`BearerAuth` (herdado por toda rota) + `Route.Summary`/`Description`/`OperationId`/`Tags`(override)/`BearerAuth`(override)/`RequestBody`/`Response`/`PathParams`/`QueryParams`/`ExcludeFromDocs`/`Deprecated` + `Metadata.Title` (nome de schema em `components.schemas`, default = nome do tipo Go). `internal/openapi.Generate(doc, root)` percorre a árvore de módulo INTEIRA (via `App.Root()`, novo -- `Module.ImportedModules()`/`OwnControllers()`/`Controller.OwnRoutes()` já existiam mas nada expunha o ponto de entrada) e gera `paths`+`components.schemas`, dedup por identidade de ponteiro de `*Metadata` (`$ref` reuso).

### AD-013: Pipe removido, `Custom(fn)` substitui, `MustJsonBody` unificado com `MustParams`/`MustQuery` via população reflect compartilhada (2026-07-14)

**Decision:** `Pipe` (feature de Milestone 3, `internal/pipe`, `Route.Param`/`PipeFor`, `gonest.Pipe`/`NewPipe`) e o `MustParam[T](ctx, name)` avulso foram REMOVIDOS de vez (commit `db19cfc`). Substitutos: `MustParams[T](ctx)`/`MustQuery[T](ctx)` (whole-object, mesma forma de `MustJsonBody`, validam TODOS os path/query params de uma rota contra `NewMetadata[T]` de uma vez) + `PropertyBuilder.Custom(fn func(raw any) (any, error))` (escape hatch de transform arbitrário dentro da própria declaração de Metadata, substitui a intenção original de Pipe). Como `Custom(fn)`'s valor de retorno precisa chegar no `T` final, `MustJsonBody` (já fechado nesta MESMA sessão, AD-012) foi refatorado: seu passo final deixou de ser `json.Unmarshal(body, result)` direto e virou `populate(...)`, uma função NOVA compartilhada pelos 3 pontos de entrada (`MustJsonBody`/`MustParams`/`MustQuery`) que popula `T` campo-a-campo via reflect, usando `Custom(fn)` quando setado.
**Reason:** processo de especificação (não INSIGHT.md pronto) — ROADMAP.md só dizia "MustParam[T] integra Pipe + coerção via metadata", vago demais pra especificar direto. 3 rodadas de `AskUserQuestion` + o usuário editando INSIGHT.md com metacódigo diretamente resolveram: (1) API whole-object (`MustParams`/`MustQuery`) em vez de per-param; (2) substituição total do `MustParam` avulso, não coexistência; (3) remoção total de Pipe, não manutenção paralela; (4) `Custom(fn)` como substituto de Pipe, dentro de Metadata; (5) unificação de `MustJsonBody` no mesmo mecanismo, aceitando reabrir código já fechado, em vez de deixar `MustJsonBody` como exceção permanente sem `Custom`.
**Trade-off:** blast radius real — INSIGHT.md reescrito em 3 seções (exemplo mais simples, Middleware/Guard/Interceptor/Filter, seção de Param/Query), `MustJsonBody`'s mecanismo interno mudou (comportamento observável idêntico, confirmado por evaluator via suite existente sem NENHUMA mudança de asserção). `setField` (novo, parte do `populate`) usa fallback JSON marshal/unmarshal pra tipos compostos (struct/slice/map aninhados) em vez de reflect puro — pragmático, reusa `encoding/json` já testado, evaluator confirmou são.
**Impact:** qualquer novo ponto de entrada de validação futuro (se houver) deve usar `populate`/`validateValue` compartilhados, não reinventar mecanismo próprio. `Custom(fn)` é chamado ATÉ 2X por campo (uma vez em `validateValue` pra checar erro, outra em `populate` pra pegar o valor) — documentado como aceitável (fn deve ser idempotente), não cacheado deliberadamente (ver design.md da feature). `KindValue()`/`CustomFunc()` (junto de AD-012's getters) são a superfície completa que Milestone 7 (OpenAPI) vai precisar ler.

### AD-012: Storage de branch-wrapper relocado pro `PropertyBuilder` compartilhado + campo `kind` novo (2026-07-14)

**Decision:** `StringMetadata`/`NumericMetadata`/`ArrayMetadata`/`ObjectMetadata` não guardam mais NENHUM campo próprio (`min`/`max`/`pattern`/`item`/`itemRef`/`ref`/`additionalProperties`) -- tudo migrou pro `PropertyBuilder` compartilhado (o único objeto que `Metadata.properties[offset]` de fato retém). Cada wrapper vira uma "view" fina que só existe durante a chain de declaração; a API pública de cada um (`Min`/`Max`/`Pattern`/`Items`/`Object`/`MinValue`/etc) fica IDÊNTICA -- puro realocamento interno via Go's promoted-field access (mesmo pacote, então campo não-exportado promovido funciona sem tocar method body nenhum). Além disso, `PropertyBuilder` ganhou campo `kind string` novo (valores OpenAPI: `string`/`integer`/`number`/`boolean`/`array`/`object`), setado por TODO método de branch -- resolve colisão pré-existente onde `String()` e `Boolean()` ambos deixavam `format == ""`, indistinguíveis.
**Reason:** descoberto especificando "JSON Body Validation" (Milestone 6) -- o validador precisa LER `Min`/`Max`/`Pattern`/etc de volta a partir de um `*Metadata` já construído, mas nada disso sobrevivia além da closure de `NewMetadata[T]` (wrapper descartado, ninguém guarda referência). Confirmado empiricamente pela própria nota SPEC_DEVIATION do dev de "Array Builder" T1 (aceita na época como não-bloqueante -- virou bloqueante aqui). `kind` resolve um segundo gap: sem ele, o validador não teria como saber se um valor JSON `true` deveria ser `boolean` ou rejeitado como `string` mal-formada, já que `format` sozinho não distingue os dois branches.
**Trade-off:** nenhum na API pública (mesmos 4 wrappers, mesmos métodos, mesmo comportamento observável). Único trade-off real: `ArrayMetadata` PRECISOU manter seu próprio campo `item *PropertyBuilder` (snapshot, populado como cópia do ponteiro no momento de `Array()`) em vez de deletá-lo como planejado originalmente -- só assim `TestArray_CalledTwice_ProducesIndependentItemState` (2 chamadas de `Array()` no mesmo campo produzindo item independente) continua funcionando. Evaluator verificou que isso não quebra o path de leitura real (`PropertyBuilder.ItemBuilder()` sem NENHUM wrapper) com teste próprio, independente do dev.
**Impact:** qualquer feature futura que precise LER metadata já declarada (ex: Milestone 7 OpenAPI generator) usa só `*PropertyBuilder`'s próprios getters (`MinValue`/`MaxValue`/`PatternValue`/`ItemBuilder`/`ItemRef`/`MetadataRef`/`IsAdditionalProperties`/`KindValue`) -- nunca precisa dos tipos wrapper (`StringMetadata` etc), que ficam só como açúcar sintático de declaração. `KindValue()` é a fonte de verdade pra "que tipo primitivo é esse campo", não `FormatValue()` sozinho.

### AD-011: `Array()`/`Items()` usa callback (`func(m *ArrayMetadata)`), reversão parcial de AD-002 (2026-07-14)

**Decision:** `ArrayMetadata.Items(fn func(m *ArrayMetadata))` recebe um CALLBACK que roda com o MESMO `*ArrayMetadata` como parâmetro (não builder linear puro devolvendo tipo novo pra encadear). Dentro do callback, `m.Required()`/`Nullable()`/`Description()`/`Examples()` SEMPRE mutam o campo container; `m.String()`/`m.Integer()`/etc SEMPRE configuram um item `*PropertyBuilder` sintético interno (nunca registrado em `Metadata.properties`), reusando `StringMetadata`/`NumericMetadata` já existentes sem duplicar código. `Min`/`Max` chamado no `*ArrayMetadata` direto (dentro do callback sem ter passado por `.String()`/etc, ou encadeado FORA depois de `Items(fn)` retornar) = quantidade do array; `Min`/`Max` chamado no wrapper devolvido por `m.String()`/`m.Integer()` = bounds do item. Ver `.specs/features/array-builder/design.md`'s Tech Decisions.
**Reason:** AD-002 (builder linear, sem callback) assumia que dá pra resolver toda ambiguidade de escopo só com ordem de chain -- mas `Array()`/`Items()` tem DOIS escopos reais que coexistem na mesma expressão (campo container vs item), e um builder linear puro não tem como saber se `Required()` chamado depois de `Items().String().Min(1).Max(50)` significa "o item é required" ou "o campo é required" (INSIGHT.md's exemplo real deixa claro que é sempre o campo -- `Description("Tags do usuário")` claramente descreve o campo, não o item). O usuário revisou o INSIGHT.md diretamente nesta sessão pra fixar isso: callback com escopo (`m` sempre = `*ArrayMetadata`) resolve, porque cada método (`Required` vs `String`) sabe estruturalmente qual estado mutar, sem depender de posição na chain.
**Trade-off:** Array/Object (e só esses dois) voltam a ter callback, quebrando a promessa de "tudo builder linear" que AD-002 fez pros branches primitivos (String/Numeric/Boolean/DateTime continuam 100% lineares, sem callback -- só Array/Object precisam do escopo duplo). Não é regressão de AD-002 pros primitivos, é reconhecimento de que Array/Object são estruturalmente diferentes (2 `PropertyBuilder`s reais coexistindo, não 1).
**Impact:** "Object Builder" (próxima feature de Milestone 5) deve seguir o mesmo padrão de callback com escopo (`ObjectMetadata` como parâmetro do callback), pelo mesmo motivo -- ver ROADMAP.md.

### AD-008: Pipeline-stage types (Middleware/Guard/futuro Interceptor/Filter) não suportam MustInject em v1 (2026-07-13)

**Decision:** `Middleware`/`Guard` (e provavelmente `Interceptor`/`Filter` quando construídos) rodam `New(fn)` IMEDIATAMENTE (mesmo padrão de `route.New`), sem suporte a `MustInject` dentro do builder — diferente de `Provider`/`Controller`/`Module`, que deferem `fn` até `Declare()` especificamente pra permitir `MustInject` resolver contra árvore de módulo já montada.
**Reason:** decisão explícita do usuário nesta sessão, perguntada via AskUserQuestion antes de especificar "Guard". `Provider` tem exatamente 1 módulo dono (imposto pelo grafo de DI via `Module.Providers`). Um `*Guard`/`*Middleware` pode ser anexado a MÚLTIPLOS controllers em módulos DIFERENTES (`controller.Guards(sameGuardVar)` reusável) — não existe "dono" único claro pra resolver `MustInject` contra sem inventar semântica ambígua nova (primeiro anexo vence? cascata por módulo? nenhuma dessas tem exemplo real no INSIGHT.md ou ROADMAP.md que justifique a complexidade agora).
**Trade-off:** exemplos do INSIGHT.md que usam `MustInject` dentro do builder de Guard/Interceptor (`AuthGuard`, `TimingInterceptor`) precisam ser adaptados nos testes — capturar a dependência de outro jeito (valor já construído fechado via closure), não via injeção de verdade. Se uma necessidade real de DI dentro de pipeline-stage aparecer no futuro, essa decisão precisa ser revisitada com um modelo de ownership novo (não é bloqueio permanente, só não resolvido ainda).
**Impact:** toda feature futura de Milestone 3 (`Interceptor`, `Filter`) deve seguir o mesmo padrão até decisão em contrário — `New(fn)` roda `fn` imediato, sem MustInject, mesma razão.

### AD-007: `NewApp[T]` genérico usa idiom de 2 type param pra suportar valor + método pointer-receiver (2026-07-13)

**Decision:** `NewApp[T any, PT httpAdapterPtr[T]](root *module.Module)` com `type httpAdapterPtr[T any] interface { *T; HttpAdapter }` (constraint), construção via `PT(new(T))`. Go infere `PT` a partir de `T`, então call site continua com 1 type arg só: `gonest.NewApp[gonest.FiberApp](AppModule)` — exatamente como já documentado no INSIGHT.md (T por valor, não ponteiro).
**Reason:** `INSIGHT.md` já fixava o call site como `NewApp[gonest.FiberApp](...)` (T por valor) antes de T8 rodar — mas `FiberApp` só satisfaz `HttpAdapter` via método de ponteiro (`*FiberApp`), então `T HttpAdapter` sozinho não compila (`FiberApp` valor não implementa a interface, só `*FiberApp` implementa). O idiom de 2 type param (T + PT constrained a `*T` satisfazendo a interface) é o jeito padrão em Go de resolver "quero só nomear o tipo base, mas a interface só é satisfeita pelo ponteiro".
**Trade-off:** `FiberApp` (e qualquer adapter futuro) precisa de um hook de init idempotente separado do zero-value construction (`Init()`, chamado 1x pelo `NewApp[T]` genérico logo após `PT(new(T))`) — zero-value de struct com campo `*fiber.App` não-inicializado precisa desse passo extra pra não nil-panicar. `fiberapp.New()` (API pública já existente de T7) passou a delegar pra `Init()` internamente, sem quebrar os testes originais de T7.
**Impact:** qualquer adapter HTTP futuro que implemente `HttpAdapter` (não só Fiber) precisa seguir o mesmo padrão: métodos pointer-receiver + `Init()` idempotente que aloca estado real, chamável em cima de um zero-value.

### AD-004: 1 pacote Go por tipo sob internal/, root só reexporta (2026-07-12)

**Decision:** cada tipo do grafo de DI (`Scope`, `Module`, `Provider`, `Controller`, motor de resolução) vive no seu próprio pacote sob `internal/` (`internal/scope`, `internal/module`, `internal/provider`, `internal/controller`, `internal/resolve`, `internal/resolver`). A raiz `gonest` só reexporta via alias de tipo (`type Scope = scope.Scope`) e wrapper fino de função (funções genéricas não dá pra reexportar via `var` em Go, viram wrapper real chamando a interna).
**Reason:** duas motivações. (1) Resolve L-003 (colisão de compilação entre sub-agents concorrentes escrevendo tipos no mesmo pacote) — T4/T5 voltam a ser paralelizáveis de verdade porque ficam em pacotes diferentes. (2) Privacidade real: usuário do pergunta explícita ("assim fica tudo privado") — com pacote único, qualquer campo não-exportado dentro de `gonest` era acessível por QUALQUER outro tipo do mesmo pacote (Module podia ver campo interno de Provider sem querer); com `internal/*` separado por tipo, só o que cada pacote exporta é visível pros outros `internal/*`, e nenhum external consumer da lib alcança nada disso (barreira dupla: Go `internal/` + fronteira de pacote).
**Trade-off:** mais arquivos de shim/reexport na raiz, mais boilerplate pra manter (`type X = pkg.X`); acesso entre `internal/*` precisa de accessor exportado explícito em vez de campo direto (mais verboso, mas intencional).
**Impact:** T2 (scope.go) migrado retroativamente pra `internal/scope` (commit `d7f1216`). design.md e tasks.md de "Provider & DI Graph" atualizados com o novo layout de `Location`/`Where`. T3 (Module) agora sequencial antes de T4/T5 (T4/T5 dependem de `module.Owner`), mas T4 (`internal/provider`) e T5 (`internal/controller`) voltam a ser `[P]` de verdade.

### AD-001: Fluxo de trabalho em 3 papéis por feature (2026-07-12)

**Decision:** cada feature roda em loop com 3 papéis: planner (Specify+Tasks) → developer (Execute, 1 sub-agent por task) → evaluator (2º sub-agent, distinto do developer, checa `Done when`/`Tests`/`Gate` de `tasks.md` contra o código real antes de marcar task como completa).
**Reason:** time pequeno/solo, precisa manter consistência sem revisão humana constante em cada task; separar quem implementa de quem valida evita "marcar como feito" sem verificação real.
**Trade-off:** mais overhead de contexto por task (2 dispatches de sub-agent em vez de 1) — aceitável dado o objetivo de consistência acima de velocidade.
**Impact:** toda Execute de tasks.md deve, após o developer sub-agent reportar Complete, disparar um evaluator sub-agent separado antes de atualizar status pra COMPLETE no tasks.md/ROADMAP.md.

### AD-003: Skills developer/evaluator vendorizadas em .agents/skills (2026-07-12)

**Decision:** `test-driven-development` (papel developer) e `verification-before-completion` (papel evaluator) copiadas de `superpowers` (v6.1.1) pra `.agents/skills/` do projeto, junto do `tlc-spec-driven` já vendorizado. `code-review` fica só como slash command global (`/code-review`), não vendorizado — não é skill no formato SKILL.md.
**Reason:** AD-001 define fluxo planner→developer→evaluator; vendorizar garante que a versão da skill usada nesse projeto não muda se o plugin global atualizar/for removido.
**Trade-off:** skill vendorizada pode ficar desatualizada em relação ao plugin global — precisa recopiar manualmente se quiser a versão nova.
**Impact:** sub-agent developer deve invocar `test-driven-development`; sub-agent evaluator deve invocar `verification-before-completion` (+ `/code-review` opcional como 2ª camada).

### AD-002: Metadata builder é linear (builder), não callback aninhado (2026-07-12)

**Decision:** `Array()`/`Object()`/`Items()` usam builder linear encadeável (`m.Property(&t.X).Array().Items().String().Min(0).Max(100)...`), não callback com escopo próprio (`Array(func(a){...})`). `Items()` é variádico (`Items(ref ...*gonest.MetadataDefinition)`) — zero-arg encadeia branch primitivo, um-arg recebe metadata já registrada pra reuso (equivalente `$ref`).
**Reason:** builder permite mesclar validações (Required/Nullable/Description/Examples) na mesma chain sem separação rígida "dentro/fora do callback"; evita bug de overload (Go não permite dois métodos com mesmo nome, callback approach anterior colidia nisso). Registrado após iteração comparando INSIGHT.md (callback) vs METADATA.md (builder) — ver histórico de conversa.
**Trade-off:** precisa de contrato claro sobre onde `Min`/`Max` se aplica (item vs array) já que não tem mais escopo de callback separando os dois níveis.
**Impact:** Milestone 5 (Array & Object builder) deve implementar `Items` como variádico e documentar a semântica item-vs-array de `Min`/`Max` no código (comentário ou doc), não só no INSIGHT.md.

### L-004: evaluator de T3 não pegou colisão de interface não-exportada entre pacotes (2026-07-12)

### L-006: pending edges eram estado global ao processo, corrigido antes de T10 (2026-07-12)

### L-012: `Pipe.Declare()` e `ctx.WithRoute()` nunca eram chamados em produção — só testes internos "trapaceavam" chamando manualmente (2026-07-13)

**Context:** ao especificar a feature "Pipe" de Milestone 3, descobri que `internal/pipe` JÁ EXISTIA (construído em T3 de "Controller & Route Registration") — só faltava re-export raiz. Ao adicionar `pipe.go`/`pipe_test.go` na raiz e escrever o primeiro teste que reproduz `ParseIntPipe` do INSIGHT.md via dispatch HTTP REAL (`app.Test`, não construção manual isolada), o teste falhou de duas formas sucessivas.
**Problem:** (1) `pipe.New(fn)` defere `fn` (que registra `Handler`) até `Declare()` rodar — mas nada no bootstrap de DI (`internal/app`'s `declareAll`) percorre Pipes anexados a Routes pra declará-los, já que Pipes não são rastreados por nenhum Module. Todo teste interno de Pipe/Route que usava Pipe customizado chamava `p.Declare()` MANUALMENTE antes de usar — mascarando que ninguém faz isso em produção. (2) `ctx.WithRoute(route)` nunca era chamado em nenhum lugar do fluxo real de dispatch — `MustParam[T]` depende disso pra achar Pipe customizado via `ctx.Route()`; sem isso, sempre caía no `defaultCoerce` genérico, ignorando silenciosamente qualquer Pipe customizado anexado.
**Solution:** `Route.Param(name, p)` agora chama `p.Declare()` antes de armazenar (commit `b305e70`). `internal/app`'s `registerRoutes` agora envolve o handler final de cada rota com uma camada que chama `ctx.WithRoute(currentRoute)` como primeiro passo, antes de middleware/guard/interceptor/handler (commit `2d3e0c3`). Evaluator independente confirmou PASS, incluindo checagem específica de que o subteste "caminho válido" sozinho não provaria a correção (já que `defaultCoerce` também converteria corretamente) — só o subteste "caminho inválido → 400 estruturado" prova de forma inequívoca que o Pipe customizado rodou (defaultCoerce nunca produz Exception estruturada, só panic genérico → 500).
**Prevents:** dois padrões a vigiar em features futuras (Filter, Pipeline Ordering): (a) qualquer tipo com padrão `New(fn)` deferido (`Declare()`-based) precisa ter, em algum lugar do fluxo de PRODUÇÃO (não só em teste), uma chamada real a `Declare()` — se só teste chama manualmente, é sinal de gap; (b) testes que só validam uma peça isolada (Pipe sozinho, Route sozinho, com `Declare()`/`WithRoute()` chamados à mão) NUNCA vão pegar um bug de fiação entre peças — só um teste que sobe a app inteira e dispara request HTTP real prova que as peças estão conectadas de verdade. Testes raiz (`pipe_test.go`, `guard_test.go` etc) não são redundantes com os testes de `internal/*` justamente por isso — são o único lugar que testa o produto inteiro, não cada peça sozinha.

### L-011: design.md descreveu ordem de composição Guard/Interceptor invertida — achado só na revisão pós-implementação (2026-07-13)

**Context:** design.md da feature "Interceptor" (escrito pelo orquestrador, EU) especificou que a chain de interceptors envolveria a saída de `gatedHandler` (que já contém Guards + Handler). O dev sub-agent de T3 seguiu esse algoritmo à risca (corretamente — instrução explícita foi "siga o algoritmo exato"), implementou e testou de acordo.
**Problem:** essa composição produz ordem de EXECUÇÃO real Middleware → Interceptor(before) → Guard → Handler → Interceptor(after) — ou seja, a lógica "before" de um Interceptor roda ANTES do Guard decidir se a request pode prosseguir. Isso contradiz ROADMAP.md (documentado como "Middleware → Guard → Interceptor → Pipe → Handler" desde o início do projeto) e o próprio propósito de um Guard: rejeitar a request antes de QUALQUER trabalho subsequente rodar, incluindo setup de Interceptor (ex: começar a medir tempo de uma request que nem devia ter sido processada por falta de auth não faz sentido). O dev sub-agent notou a divergência entre design.md/tasks.md's prosa (que dizia a ordem certa) e o bloco de código do próprio design.md (que produzia a ordem errada), documentou como SPEC_DEVIATION e seguiu o código literal — decisão correta da parte dele (escopo dele não autorizava reordenar a composição por conta própria), mas expôs um erro real que só foi pego porque ele reportou a divergência explicitamente em vez de simplesmente "resolver" silenciosamente pra um lado ou outro.
**Solution:** corrigido design.md (bloco "Composition change" e diagrama) pra descrever a ordem certa (Interceptor envolve o `routeHandler` bruto; Guard envolve o RESULTADO disso, não o `routeHandler` direto — Guard fica mais externo). Dev sub-agent corrigiu `internal/app/app.go` (troca de ordem de wrapping, 1 linha efetivamente) + testes (reverteu a asserção de ordem pro valor certo, removeu o comentário SPEC_DEVIATION que documentava o comportamento errado, adicionou teste novo provando que Guard rejeitando bloqueia tanto Handler quanto Interceptor-before). Evaluator re-verificou tudo, PASS.
**Prevents:** ao desenhar composição de múltiplos estágios de pipeline que se envolvem uns aos outros (Middleware/Guard/Interceptor/Pipe), sempre TRAÇAR a ordem de EXECUÇÃO resultante do algoritmo de composição escrito (não só a ordem de "quem chama quem no código-fonte") e comparar contra a ordem documentada no ROADMAP/spec ANTES de mandar pro developer — um algoritmo de "A envolve B" tecnicamente correto sintaticamente pode produzir ordem de execução semanticamente errada se a direção do wrapping (quem é mais externo vs mais interno) não bater com a ordem pretendida. Sub-agents que notam divergência entre prosa e código do próprio design devem SEMPRE reportar como SPEC_DEVIATION explícito (nunca resolver silenciosamente pra um lado) — foi exatamente isso que permitiu pegar esse erro rápido.

## Lessons Learned (cont. 9)

### L-010: `httpctx.Context.Header()`/`SetHeader()` são stores diferentes (request vs response) — não dá pra "ler, concatenar, escrever de volta" (2026-07-13)

**Context:** T4 da feature "Middleware" tentou provar ordem de execução de múltiplos middlewares fazendo cada um ler o header atual, concatenar um marcador, escrever de volta (`ctx.Header(...)` → `ctx.SetHeader(...)`) — técnica sugerida no dispatch da task.
**Problem:** `Context.Header(name)` delega pra `Responder.GetHeader`, que no `fiberResponder` real (`internal/fiberapp`) mapeia pra `fiber.Ctx.Get` — isso lê o header da REQUEST recebida, não da resposta sendo construída. `Context.SetHeader(name, value)` delega pra `Responder.SetHeaderValue` → `fiber.Ctx.Set`, que escreve no header da RESPONSE. São dois stores completamente diferentes — "ler o que acabei de escrever" nunca funciona através de `Header()`/`SetHeader()`, porque `Header()` nunca vê o que `SetHeader()` gravou.
**Solution:** T4 adaptou pra 3 técnicas alternativas, todas via dispatch real (`app.Test`): (1) slice `[]string` compartilhado via closure pra provar ordem, (2) `resp.Header` do `*http.Response` real (o que efetivamente chegou no wire) pra provar presença/valor final, (3) `ctx.WithRoute`/`ctx.Route()` (campo `any` genérico, normalmente usado pra anexar `*route.Route` pro `MustParam`) reaproveitado como carrier de valor arbitrário pra provar que múltiplos middlewares/Handler enxergam a MESMA instância de `*Context` — evaluator confirmou isolamento (nenhum teste que usa essa técnica também depende de `MustParam` via Pipe-por-Route na mesma request).
**Prevents:** qualquer teste futuro que precise "ler o header que acabei de setar, dentro da mesma request, através da API pública de `Context`" precisa saber que isso não é possível hoje — `Header()` é só request-read. Se essa capacidade (ler resposta já escrita) vier a ser necessária de verdade (não só em teste), precisa de um método novo tipo `Context.GetResponseHeader` — não existe ainda.

## Lessons Learned (cont. 8)

### L-009: Fiber v3 `Ctx.Params()` devolve view zero-copy sobre buffer reusado — precisa `strings.Clone` (2026-07-13)

**Context:** T9 (exemplo end-to-end `UserController`) escreveu `UserService.Create(name)` guardando `name` (vindo de `ctx.Param`→`fiberResponder.GetParam`→`fiber.Ctx.Params()`) num campo de struct persistido além da vida da request. Testes ficaram flaky, valor corrompido (`"1da"` em vez de `"Ada"`).
**Problem:** `fiber.Ctx.Params()` (fasthttp por baixo) devolve string sobre um buffer reusado entre requests — doc do Fiber diz explicitamente "Returned value is only valid within the handler... Make copies to use the value outside the Handler". `fiberResponder.GetParam` (`internal/fiberapp/fiberapp.go`, criado em T7) repassava o valor cru, sem copiar — qualquer handler que persiste o valor (mesmo indiretamente, via struct guardado em serviço singleton) corre risco de ver o valor de uma request seguinte sobrescrever o buffer.
**Solution:** `GetParam` agora faz `strings.Clone(r.c.Params(name))`. Evaluator do T9 reproduziu o bug de propósito (reverteu o fix, rodou o teste novo 30x, 19 falhas com o padrão exato de corrupção previsto) antes de confirmar o fix — não foi só aceitar a alegação do dev sub-agent.
**Prevents:** qualquer novo código em `internal/fiberapp` (ou adapter HTTP futuro) que leia string de `fiber.Ctx` (`Params`, possivelmente `Query`/outros getters zero-copy do fasthttp) e a repasse pra fora do escopo da request precisa copiar explicitamente — não assumir que string do Fiber/fasthttp é segura pra reter.

## Lessons Learned (cont. 7)

### L-008: `Context.route any` + assertion — deveria ter sido interface tipada (2026-07-13)

**Context:** T5 (feature Controller & Route) precisou ligar `httpctx.Context` a `*route.Route` (pra `MustParam` checar `HasParam`), mas `internal/route` já importa `internal/httpctx` — importar de volta ciclaria. Solução usada: `Context.route any` + type assertion em `route.MustParam`.
**Problem:** evaluator apontou que uma interface pequena definida DENTRO de `httpctx` (`type paramHost interface { HasParam(string) bool }`), satisfeita estruturalmente por `*route.Route`, resolveria o mesmo ciclo com segurança de tipo em compile-time — sem `any` + assertion que degrada silenciosamente pra "sem rota" em qualquer type mismatch.
**Solution:** não corrigido ainda (não bloqueia T5) — registrado como débito. Só 1 call site (`route.MustParam`) usa isso hoje, fica mais barato de trocar agora do que depois que mais coisa acoplar.
**Prevents:** quando precisar ligar 2 pacotes que já têm import na direção oposta (evitar ciclo), preferir interface pequena definida no pacote "de baixo" (satisfeita estruturalmente pelo de cima) em vez de `any`+assertion — mesmo custo de acoplamento, ganha segurança de tipo.

## Recent Decisions (cont.)

### AD-006: MustResolve renomeado pra MustInject (2026-07-12)

**Decision:** `MustResolve[T]` (API pública) → `MustInject[T]`; `internal/resolve` (pacote que implementa) → `internal/inject`. `internal/resolver` (motor de grafo/DFS/Stage 3 — `Find`/`BuildGraph`/`DetectCycle`/`Resolve`) **não** renomeado, fica como está — é implementação interna, nunca exposta.
**Reason:** evitar colisão de vocabulário com "Resolver" do GraphQL (field resolvers), caso o projeto suporte GraphQL no futuro. Também alinha mais com `@Injectable`/`@Inject` do Nest, que o projeto já mira imitar.
**Trade-off:** nenhum funcional — rename puro, mesmos 95 testes antes/depois, mensagem de panic atualizada (`"gonest: MustInject[T] requires T to be a pointer type..."`).
**Impact:** `INSIGHT.md` atualizado (14 ocorrências). `.specs/features/provider-di-graph/*.md` **não** tocados de propósito — ficam como registro histórico do que foi construído na época (ainda dizem `MustResolve`). Qualquer feature nova a partir de agora usa `MustInject` como referência.

### AD-005: Transient sem consumidor nunca instancia (lazy), diferente de Singleton (eager) (2026-07-12)

**Decision:** provider `ScopeTransient` com zero pending edges apontando pra ele (nenhum `MustResolve` chamado) nunca roda `Constructor` — `Resolve()` não gera evento de resolução se não existe chamada. Singleton continua eager: T9's `allProviders` resolve todo mundo registrado independente de uso.
**Reason:** spec.md P2 diz literalmente "cada `MustResolve[T]` roda `Constructor`" — condicionado a existir a chamada. Verificado empiricamente pelo evaluator de T10 (zero `MustResolve` = zero execução, sem erro/deadlock).
**Trade-off:** assimetria real entre os 2 scopes — Provider Transient declarado só por efeito colateral (ex: logger/registrador sem consumidor) nunca roda, silenciosamente, sem erro. Pode surpreender um dev que espera paridade com Singleton.
**Impact:** documentado aqui (evaluator pediu nota durável, não só no relatório do sub-agent) — se abrir issue de "provider X não roda", checar primeiro se é Transient sem `MustResolve` nenhum apontando pra ele antes de assumir bug.

## Lessons Learned (cont. 6)

### L-007: `git commit` sem pathspec pega o índice inteiro, não só o que o sub-agent adicionou (2026-07-12)

**Context:** T1 e T2 (feature Controller & Route Registration) rodaram em paralelo de verdade pela 1ª vez desde a correção de AD-004 (pacotes diferentes: `internal/route` vs `internal/httpctx`). Ambos fizeram `git add <arquivos próprios>` e `git commit` sem pathspec.
**Problem:** `git add <arquivos>` só adiciona esses arquivos ao índice — mas o índice é compartilhado entre processos concorrentes no mesmo working dir. Se o agent B faz `git add` entre o `git add` e o `git commit` do agent A, o `git commit` (sem pathspec) do agent A commita o índice INTEIRO, incluindo os arquivos que B acabou de stagear — não só os que A pediu. Os dois sub-agents desse dispatch pegaram isso sozinhos (via `git show --stat HEAD` depois de commitar) e corrigiram com `git reset --soft HEAD~1` + `git restore --staged` nos arquivos do outro.
**Solution:** nenhuma ação corretiva nesse caso — ambos sub-agents detectaram e resolveram por conta própria antes de reportar. Mas o padrão vai se repetir em todo dispatch paralelo futuro.
**Prevents:** ao dispatchar tasks paralelas que fazem commit próprio, instruir explicitamente pra usar `git commit -- <arquivo1> <arquivo2> ...` (commit com pathspec, escopado só aos arquivos listados) em vez de `git commit` puro — elimina a janela de corrida sem precisar de `git show --stat` defensivo depois.

## Active Blockers

### B-001: `-race` quebrava por CC=clang injetado no processo shell (2026-07-12) — RESOLVIDO

**Discovered:** T2, no gate check (`clang: error: unsupported option '-mthreads' for target 'x86_64-pc-windows-msvc'`).
**Impact:** bloquearia o Gate de toda task Go daqui em diante (não era específico do código de T2 — reproduzido pelo evaluator, erro ocorre compilando `runtime/cgo` antes de qualquer código do projeto).
**Root cause:** processo que spawna cada shell da sessão injeta `CC=clang` (target MSVC) — não é variável User/Machine persistida do Windows (essas estavam vazias), então nem `go env -w` nem `setx`/`SetEnvironmentVariable` conseguem sobrepor sem reiniciar a sessão do harness.
**Workaround:** MinGW-w64 instalado via `winget install BrechtSanders.WinLibs.POSIX.UCRT`; Gate command em TESTING.md agora prefixa `CC=gcc CXX=g++ PATH=".../mingw64/bin:$PATH"` inline em todo comando de teste. Confirmado funcionando (T2 passou com `-race` depois disso).
**Resolution:** definitivo seria reiniciar a sessão do harness pra ver se `CC=clang` some do processo — até lá, o prefixo inline no Gate command é a solução permanente-o-suficiente. Revisar quando/se reiniciar a sessão.

### L-001: Go não permite parâmetro de tipo em método (2026-07-12)

**Context:** design inicial do metadata builder tentou `Object[AddressEntity]()` como método genérico.
**Problem:** Go só permite type parameter em func livre ou tipo, nunca em método — não compila.
**Solution:** metadata aninhada é capturada como valor (`addressMetadata := gonest.NewMetadata[AddressEntity](...)`) e passada explicitamente pra `Object(addressMetadata)`/`Items(addressMetadata)`, sem reflect e sem genérico em método.
**Prevents:** qualquer novo builder que precise "saber o tipo T" dentro de um método deve usar esse padrão (valor capturado), não tentar `.Method[T]()`.

## Preferences

**Model Guidance Shown:** never

**Commit convention (2026-07-15):** every commit, every iteration/task, MUST be in en-US, using Conventional Commits format (`type(scope): summary`, e.g. `feat(emitter): add Emitter/Listener/MustOn`, `docs(specs): close Emitter feature`, `refactor(app)!: ...` for breaking changes). Types used so far in this project: `feat`, `fix`, `refactor` (with `!` suffix for breaking changes), `docs`. Body (when present) explains WHY, not WHAT (the diff already shows what changed) -- see git log for the established tone/depth. Applies regardless of what language the conversation itself is happening in (this repo's own conversations are often in pt-BR, but commits stay en-US).

**Subagent workflow convention (2026-07-17, decided during Milestone 14 planning -- applies to EVERY feature from now on, not just this one):** toda `tasks.md` a partir de agora é escrita já pensando em 3 papéis de subagente distintos, delegados via o `Agent` tool:
- **Planner** -- roda UMA vez por feature, depois que `spec.md`/`design.md` já existem. Recebe spec+design+CONVENTIONS.md/TESTING.md (quando existirem) e produz `tasks.md`: quebra em tasks atômicas, marca `[P]` as paralelizáveis, declara `Depends on`/`Reuses`/`Done when`/`Tests`/`Gate`/`Commit` por task (mesmo formato que `references/tasks.md` do skill já usa) -- MAS cada task já deve ser granular o bastante pra virar o prompt INTEIRO de um Implementer sem contexto adicional.
- **Implementer** -- um subagente POR task (ou por grupo `[P]` em paralelo). Recebe SÓ a definição daquela task (What/Where/Depends on/Reuses/Done when/Tests/Gate) + convenções de código relevantes -- NUNCA recebe as outras tasks, o histórico da conversa, nem relatórios de avaliação de tasks anteriores. Implementa e reporta: Status (Complete/Blocked/Partial), Files changed, Gate check result, SPEC_DEVIATION (se houver).
- **Evaluator** -- roda DEPOIS de cada Implementer, ANTES de prosseguir pra próxima task/marcar a task como concluída. Recebe a definição da task + o diff real produzido (não o relatório do Implementer sozinho -- sempre verifica o código, nunca confia só na alegação) e confere: `Done when` bate, `Gate` passou de verdade (roda o comando, não assume), nenhum `SPEC_DEVIATION` foi introduzido silenciosamente. Aprova (task vira `completed`) ou devolve pro Implementer com o motivo específico -- NUNCA corrige o código ele mesmo (separação de papel: quem avalia não implementa a correção, isso volta pro Implementer ou vira uma nova task).
Motivo: cada papel roda com contexto MÍNIMO e ESPECÍFICO pro que precisa fazer -- Planner nunca vê código real (só specs), Implementer nunca vê outras tasks nem histórico de avaliação, Evaluator nunca escreve código -- evita que um mesmo agente "marque a própria lição de casa" e mantém cada subagente raso o bastante pra ser confiável. Este é o padrão a seguir em toda feature Large/Complex do `tlc-spec-driven` daqui pra frente, não só `request-response-split` -- ver esse `tasks.md` como referência de formato aplicado.

**Versioning convention (2026-07-15 decided, 2026-07-16 APPLIED -- first tag `v0.6.0` cut, see below):** field semantics `{major}.{minor}.{release}` under a leading `v0` fixed FOREVER (never incrementing to `v1`/`v2`) -- `major` increments on a BREAKING change (matches Conventional Commits' own `!` suffix, e.g. `refactor(app)!:`), `minor` on a new backward-compatible FEATURE, `release` on a FIX/patch with no contract change. Reasoning for the fixed `v0`: Go's own module system forces an import-path change (`/v2`, `/v3` suffix) at major version 2+ -- staying under `v0` sidesteps that permanently, AND `v0.x` already conventionally signals "no API stability guarantee yet" under semver, an honest description of this library's current state (single contributor, no dogfooding outside its own test suite). CORRECTION (2026-07-16): the original notation for this (`v0.{major}-{minor}.{release}`, a DASH between major/minor) is NOT valid semver -- confirmed empirically via `golang.org/x/mod/semver.IsValid` (`false` for `v0.6-0.0`, `true` for `v0.6.0`) -- an invalid tag `go get`/pkg.go.dev would silently fail to recognize, defeating the entire point of tagging. The actual git tag is real 3-segment semver (`v0.6.0`), the `major`/`minor`/`release` semantics above still apply to which segment increments for which kind of change, just written with dots like every other Go module. First tag's starting number (`0.6.0`, not `0.1.0`) reflects the 6 breaking (`!`) commits already in git log before this tag existed (`db19cfc`, `450656a`, `6933320`, `0531a21`, `3761e86`, `f6e4ffe`) -- user's explicit choice, historically-accurate over a clean-slate `0.1.0`.
